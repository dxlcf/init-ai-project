# 设计对话与文档撰写

## 对话如何推进

以首版应用为边界，沿关键用户路径逐步讨论。下面是覆盖面，不是必须逐项询问的问卷；已有材料能够回答的内容直接整理，不适用的部分说明原因。

| 设计主题 | 需要形成的结论 |
| --- | --- |
| 产品目标与范围 | 谁在什么场景遇到什么问题；首版解决什么、不做什么；如何判断用户获得了预期结果 |
| 用户流程 | 从入口、输入到结果的关键步骤；主要页面或 CLI/API 交互；失败、取消、重试以及需要用户确认的位置 |
| AI 行为 | 哪些步骤由模型完成，哪些由确定性代码完成；输入上下文、输出形式、质量要求；无法回答或不确定时如何处理 |
| 数据与权限 | 数据来源、核心对象、关系及存储必要性；谁能访问、是否传给外部模型、保存和删除方式 |
| 应用与集成 | 各应用及模块职责、关键调用和数据流；是否同步或后台执行；外部系统、接口和运行边界 |
| 运行与验收 | 本地或部署环境、已知负载/延迟/成本约束；关键用户路径及失败场景如何验证；尚需实验验证的技术假设 |

有检索需求时再讨论资料导入、更新、检索范围、引用及无证据时的行为；有 Agent 时再讨论工具、状态、停止条件、权限、人工确认及失败恢复。没有相关需求时不自动添加向量库、队列、多 Agent 或独立服务。

先用用户能理解的行为描述设计，再由模型提出实现建议并解释取舍。例如“任务耗时较长时用户能否离开页面，回来后继续查看结果”比直接要求用户选择消息队列更容易获得有效需求。具体技术能力按技术选型指南核实。

讨论中区分四种信息：用户已确认的结论、模型提出但尚未接受的建议、明确标注的暂定假设、真正缺失的待确认事项。注明关键结论来自哪份材料或哪项对话决定即可，不必逐句保存聊天记录。发现冲突时解释受影响的流程和设计，先解决会改变方案的分歧。

## 何时可以进入初始化

能够沿首版关键流程说明“用户做什么 → 系统或 AI 做什么 → 读写哪些数据 → 返回什么 → 失败时怎么办”，并有对应的成功标准和应用边界，即可汇总方案供用户确认。深度随产品复杂度调整，不需要提前写完全部接口字段、数据库索引或实现算法。

影响核心行为、权限或目录结构的问题应优先解决。可以后续验证的问题，记录影响、验证方式及需要解决的时机；用户明确希望先初始化时，保留这些未知项，不通过编造答案来满足完整性。已确认的技术栈不代表其余设计也获得确认。

## 各文档写什么

模板提供章节起点，可按产品增删内容；保留开发规范和自动校验所需的约定。下表是内容归属，不要求创建更多文档。

| 目标文档 | 初始化时应写入的产品内容 |
| --- | --- |
| `docs/product/brief.md` | 目标用户、问题与目标、首版范围和非目标；关键用户流程及异常行为；核心能力的可验证成功标准；数据与隐私要求；暂定假设和未决项。产品行为以此为依据，不在此重复技术方案全文 |
| `docs/architecture/overview.md` | 应用和模块职责、实际目录；沿关键流程说明调用与数据流，按需使用图；AI 输入/输出、检索或工具调用、状态及人工介入边界；权限、失败恢复和运行约束。区分计划设计与已实现状态 |
| `docs/adr/0001-technology-stack.md` | 本次选型的背景约束、选择及理由、实际讨论过的替代项和取舍、风险与待验证事项。未评估的替代项如实注明，不捏造比较；后续重要变更用新 ADR 保留历史 |
| `docs/api/contracts.md` | 有后端时生成；记录已设计的核心接口或交互契约、调用方与用途、方法/路径（已确定时）、请求和响应、鉴权、错误；按需记录流式返回、异步状态、取消和幂等。未确定的字段明确留待细化，不将通用填写说明当成实际接口设计 |
| `docs/database/data-model.md` | 有数据库时生成；记录已确定的核心实体、关系、关键字段与约束、数据归属、访问权限、保留与删除；迁移位置及已知兼容要求。未决定的类型/索引可留待实现前细化，不自动添加用户表或向量库 |
| `docs/testing/strategy.md` | 实际测试目录与测试分层；将关键成功标准对应到测试路径或人工验收方式，覆盖主要失败与权限场景；有模型质量目标时记录样例类型、评分标准和通过条件，未确定阈值时如实标注；区分计划验证和已执行验证 |
| `docs/development/sdd.md` | 保留轻量开发规则，说明未来功能规格如何引用已有产品、架构、接口和数据设计，以及需求变化时如何同步；无需为每个产品重写一套流程 |
| `README.md` | 产品摘要、设计文档导航、选型和实际结构、当前完成状态、影响下一步的未决项；未实现前不编造可执行命令 |
| `specs/_templates/{spec,plan,tasks}.md` | 保持供未来复制的通用模板，不把初始化讨论变成已开始的开发任务 |

其余 `AGENTS.md`、协作规范和配置沿用骨架规则。无后端或无数据库时，不强制生成对应专项文档；外部 API 调用、本地文件等必要的数据与集成设计可以记录在架构概览中。

## 文档撰写与验收

1. **生成底稿后补全**：脚本参数只能传递摘要、技术栈、理由和路径。逐份编辑本次目标项目的文档，将已确认设计和已授权保留的假设写入正文；产品具体内容不写回技能模板。保留未明确部分的状态，删除已解决的“待确认”和不适用的通用待办。
2. **区分创建与补全**：目标目录非空时不执行初始化或覆盖既有文件；脚本成功生成后，补全本轮新建文件是同一次授权内的必要步骤，不需要再次确认。中断恢复时先核实哪些文件属于本次生成、是否有用户修改，不重跑脚本覆盖。
3. **检查信息覆盖**：对照最终确认的方案及已有材料，检查用户、范围、关键流程、AI 行为、数据、权限和验收结论是否已落入相应文档。不能只凭文件存在或模板标题齐全判定交付完成。
4. **检查一致性**：产品流程中的能力应有架构职责和验证方式；涉及的接口、实体、权限、技术名称及目录在相关文档与配置中一致。同一事实选择主要记录位置，其他文档摘要引用，避免多处复制后产生冲突。
5. **检查真实性与交接**：已确认内容不再留空，假设不冒充需求，未决项说明影响和下一步确认/验证方式；设计不冒充实现，计划测试不冒充测试通过。报告实际检查结果和剩余限制。

自动校验负责骨架与部分规范，不能判断上述语义是否正确。完成校验后仍需人工逐项核对；若用户只授权了带未知项的初稿，按初稿交付并列出缺口。
