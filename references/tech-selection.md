# 技术选型指南（给初学者的解释方式）

## 选型顺序

1. 从用户故事出发：主要用户、最重要的操作、数据种类、隐私要求、是否需要浏览器/本地文件/命令行操作、是否需要长时间后台任务。
2. 先判断是否需要“Agent”：单轮文字生成、结构化提取等可能只要普通模型 API；需要工具调用、分步骤决策、状态追踪时再考虑编排框架；需要自主使用文件/终端/浏览器的完整助手时才评估 Harness。
3. 选能满足近期需求的**最简单可维护方案**。前端、后端、数据库、Agent 组件按需独立，不强迫每个产品都使用四套服务。
   先确定应用形态：同一全栈框架可用单应用；有独立后端或 Agent 进程时再用多应用。Agent 默认内嵌，独立依赖、权限隔离或部署需求才支持拆分；迁移跟随数据所属应用，布局见 [骨架规则](scaffold-rules.md#结构选择)。
4. 将**模型提供商**与 **Agent 框架/Harness** 分开说明：模型负责生成和推理，框架负责组织步骤与工具，Harness 常包含任务循环、工具/权限/会话等运行环境。避免把 DeepSeek 模型与 DeepSeek Harness 混为一谈。
5. 选型前通过官方文档/仓库核实可能变化的能力；新兴工具重点核查维护状态、部署方式、扩展接口、权限隔离、数据去向、许可证与锁定风险。无法联网或缺乏可靠资料时，仍可给出保守候选，但明确标注“尚未核验”，将影响落地的事项列为实施前待确认项。

## 框架与 Harness 的判断参考

| 选项 | 适合优先评估的场景 | 必须进一步核实 |
| --- | --- | --- |
| 无 Agent 框架（直接调用模型 API） | 简单问答、文本生成、分类或提取 | 是否真的需要自动工具调用/长流程 |
| OpenAI Agents SDK | 应用内工具调用、多个角色交接、希望从简单 Agent 起步 | 模型兼容、运行语言、跟踪和成本 |
| LangGraph | 多步骤、有状态、需暂停/恢复或人工审核的业务工作流 | 状态持久化、部署和维护复杂度 |
| Pi | 偏轻量、可高度扩展的编码/终端型 Harness | 如何集成到目标产品、权限隔离与运行方式 |
| DeepSeek Harness | 希望基于可组合插件自定义工具型 Agent 运行环境 | 当前版本成熟度、插件权限和实际可部署性 |
| Hermes Agent | 更接近独立个人/任务助手、希望复用已有 Agent 能力 | 是否适合作为嵌入式服务、数据存储、权限与运维 |

这些只是**候选方向**，不是按性能、流行度或“先进程度”的排名，也不是保证某框架能直接嵌入所有产品。

## 其他技术栈

- 前端：面向网页的产品常优先评估 React/Next.js、Vue/Nuxt 等；仅内部界面也可考虑更轻量方案。先考虑学习与维护成本。
- 后端：Python AI 生态可评估 FastAPI；全 TypeScript 团队可评估 NestJS/Express。除非确有必要，避免混用太多语言。
- 数据库：存在关系数据与账号/业务记录时可优先评估 PostgreSQL；低并发单机原型可考虑 SQLite。向量检索不必先单独买一套数据库，先确认是否真的需要。
